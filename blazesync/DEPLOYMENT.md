# BlazeSync — hosting, testing & environment runbook

Zero-assumption, ordered checklists. Follow top to bottom.

---

## 1. Environment variables — the complete reference

Copy `.env.example` → `.env` for local dev. In production, set the same keys
in the Render dashboard (never in files). Nothing is required to run locally:
missing Ecobank credentials simply switch the client to mock mode.

### Required everywhere

| Key | Local default | Production | What it is |
|---|---|---|---|
| `ENVIRONMENT` | `development` | `production` | Enables prod guardrails when `production` |
| `DATABASE_URL` | *(empty → embedded Postgres)* | **required** — Supabase Postgres Session Pooler URI | PostgreSQL connection string (Postgres-only by design) |
| `JWT_SECRET` | dev fallback | **required, long random value** — the app refuses to boot without it | Signs access/refresh tokens |

### Auth tuning (optional)

| Key | Default | What it is |
|---|---|---|
| `ACCESS_TOKEN_MINUTES` | `15` | Access token lifetime |
| `REFRESH_TOKEN_DAYS` | `7` | Refresh token lifetime |

### Ecobank Unified API (all optional — empty ⇒ mock mode)

Register at the Ecobank developer portal; credentials arrive by email
(`userId`, `password`, `lab_key`). In the portal's product catalogue, BlazeSync
needs **Account Enquiry** (reconciliation), **Local Bank Payment** (payouts),
**Account Opening** (members get real Ecobank accounts), and **Payment From
Ecobank Account** (direct-debit mandates + dues pulls). **Bill Payment**,
**Remittance**, and **Xpress Cash** are not used. There are **no virtual
accounts** — dues are collected by direct debit against each member's opened
account, gated on an active mandate.

| Key | What it is |
|---|---|
| `ECOBANK_USER_ID` | UserID from the sandbox registration email |
| `ECOBANK_PASSWORD` | Password from the same email |
| `ECOBANK_LAB_KEY` | Lab key — the hashing secret for `requestToken`/`secureHash` |
| `ECOBANK_CLIENT_ID` | Assigned when your app is profiled on the sandbox |
| `ECOBANK_AFFILIATE_CODE` | E.g. `ECOBANKNG` — from your onboarding docs |
| `ECOBANK_SOURCE_CODE` | Your source/channel code from onboarding |
| `ECOBANK_BASE_URL` | Sandbox base URL (default `https://sandboxapi.ecobank.com`) |
| `ECOBANK_ORIGIN` | Required `Origin` header (default `developer.ecobank.com`) |
| `ECOBANK_WEBHOOK_SECRET` | Shared secret for HMAC-SHA512 webhook signatures |
| `ECOBANK_MAX_RETRIES` / `ECOBANK_RETRY_BASE_DELAY` / `ECOBANK_TIMEOUT_SECONDS` | Outbound resilience knobs |
| `MOCK_BALANCE_DRIFT` | Mock-mode only: simulate balance drift to demo reconciliation |

### App / jobs (optional)

| Key | Default | What it is |
|---|---|---|
| `PUBLIC_BASE_URL` | `http://localhost:8000` | Your deployed base URL in prod |
| `ALLOWED_ORIGINS` | `PUBLIC_BASE_URL` | Comma-separated CORS allow-list |
| `INVITE_EXPIRY_DAYS` | `14` | Roster invite claim window |
| `RECONCILE_INTERVAL_SECONDS` | `300` | Background reconciliation cadence (0 disables) |
| `AUTO_MIGRATE` | `true` | Run `alembic upgrade head` on boot (Render build already does it → set `false` there) |

## 2. Local testing

```bash
# one-time
python -m venv .venv && source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env

# full test suite — runs against a REAL Postgres (boots an embedded cluster
# into .pgserver/ automatically; each run gets a fresh isolated schema)
pytest -q

# lint
ruff check app migrations tests

# run the API + walk the 13-step demo journey (includes the live WebSocket)
uvicorn app.main:app --port 8000
python scripts/smoke_test.py http://127.0.0.1:8000

# interactive API docs
open http://localhost:8000/docs
```

No Docker, no Postgres install, no Ecobank account needed for any of the
above — mock mode covers the full flow end-to-end.

## 3. Hosting on Render + Supabase (free tier covers the demo)

The database lives on **Supabase**, not Render — see the root
[`DEPLOYMENT.md`](../DEPLOYMENT.md) for the full walkthrough. Short version:

1. **Create a Supabase project**, then copy the **Session Pooler** connection
   string (host `...pooler.supabase.com`, port `5432`). The direct
   `db.<ref>.supabase.co` host is IPv6-only and unreachable from Render's free
   tier — use the pooler. No tables to create: migrations do it.
2. **Push the repo to GitHub.**
3. Render dashboard → **New +** → **Blueprint** → connect the repo. Render
   reads `render.yaml` and provisions the web service `blazesync-api`
   (Python 3.12, health check `/api/health`). **No Render database is created.**
4. Set the prompted env vars:
   - `DATABASE_URL` — your Supabase Session Pooler URI
   - `PUBLIC_BASE_URL` / `ALLOWED_ORIGINS` — your `https://<app>.onrender.com`
     (and your frontend origin for `ALLOWED_ORIGINS`)
   - `JWT_SECRET` — auto-generated by the blueprint; regenerate if you like
   - `ECOBANK_*` — **not declared** in the blueprint; add in the dashboard for
     mock mode → live
5. **Apply** → first deploy runs `pip install` + `alembic upgrade head` against
   Supabase, then starts uvicorn. The health check gates the deploy.
6. Verify live:
   - `https://<app>.onrender.com/api/health` → `{"status": "ok"}`
   - `https://<app>.onrender.com/docs` renders
   - Run the demo journey against prod:
     `python scripts/smoke_test.py https://<app>.onrender.com`
7. Scale story (say it to judges, don't build it yet): the service is
   stateless (JWT + revocable refresh rows), so horizontal scale = more
   instances behind the router; the reconcile loop should move to a dedicated
   worker/Celery at that point.

## 4. CI (GitHub Actions)

`.github/workflows/ci.yml` runs on every push/PR:

- **ruff** lint over `app/`, `migrations/`, `tests/`
- **pytest** against a real Postgres 16 service container (so the append-only
  trigger, unique constraints, and advisory locks are genuinely exercised)

## 5. Going live with Ecobank (post-hackathon path)

1. Complete sandbox registration; receive `userId` / `password` / `lab_key`.
2. Set the `ECOBANK_*` env vars; the client flips from mock to live
   automatically (`ecobank_mock_mode` is just "credentials present?").
3. Run the hashing known-answer tests — they assert the exact documented
   concatenation formulas, the #1 place integrations lose time:
   `pytest tests/test_ecobank_hashing.py -q`
4. Smoke-test each service in isolation with Postman (Ecobank ships a
   collection) before wiring flows; populate their test-case document as you
   go (it's required for the go-live request).
5. Register the webhook URL `POST /api/v1/webhooks/ecobank/notification` with
   Ecobank and set `ECOBANK_WEBHOOK_SECRET` to the shared signing secret.
6. Complete the go-live request on the developer portal (KYC + test-case doc).
